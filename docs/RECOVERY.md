# 换机部署与单数据库恢复

ECS 的 SSH 私钥只负责连接新服务器。密码库的主密码或恢复密钥只负责解密数据。应用容器不接收 ECS 私钥，也不绑定服务器地址或 SSH 身份。

## 需要保留什么

- 管理页下载的 `.dump` 数据库备份。它包含全部业务表、序列、加密密钥信封和数据格式版本；不需要另存旧服务器上的 `vault.json`。
- 与备份匹配的原主密码或 `recovery:...` 恢复密钥，独立于备份妥善保存。
- 对应的程序发布版本，来自可访问的 GitHub 仓库或另存的源码发布包。记录下载说明中的应用版本、数据库结构版本、PostgreSQL 版本；不要直接假定未来任意版本都能读取旧数据。
- 建议同时保存 `.sha256` 和说明文件，用于校验完整性及确定兼容版本。它们不含额外解密钥匙。

新 ECS 私钥、新机器查询启动密钥、模型文件和内存索引均可重新建立。旧 ECS 丢失不影响数据库解密；原主密码和恢复密钥都丢失则不能正常恢复。

## 从网页保存备份

1. 通过 SSH 隧道登录管理端，打开“备份与灾备”。
2. 生成数据库备份，等待任务显示就绪。它覆盖全部业务数据，不受搜索或回收站视图限制。
3. 分别下载数据库、SHA-256 和说明文件，保存到服务器之外的位置。
4. Windows 可用 `Get-FileHash -Algorithm SHA256 <备份文件>`，Linux 可用 `sha256sum -c <校验文件>`；确认字节数和摘要与说明一致。

“已开始下载”不代表下载完整或恢复验证通过。下载过程中管理端锁定不会撤回已经批准的当前传输，最多继续 30 分钟；新下载必须重新登录。此版本不支持断点续传，中断后重新登录并从头下载。默认服务器保留 7 天，本地副本由用户自行轮换。

## 全新服务器恢复

使用满足运行资源要求的 Linux ECS，准备 Docker Engine、Docker Compose、Python 3、Git、tar 和 flock。SSH 和出站网络必须可用；数据库与管理页不开放公网端口。

1. 使用新 ECS 的 SSH 身份登录新服务器，获取备份对应的兼容源码版本。下面命令在已经获取的源码根目录执行，默认状态目录是 `/var/lib/wechat-vault`。
2. 如需更改状态目录，复制 `.env.example` 为 `.env`，设置专用绝对路径 `VAULT_STATE_DIR`。源码目录与状态目录可以分开。不要把真实配置提交到 Git。
3. 以 root 执行准备、构建和数据库启动：

```sh
sh ops/deploy/bootstrap.sh --prepare-only
docker compose build app
docker compose up -d db
```

准备命令创建状态目录和权限、新机器查询密钥，并下载校验模型；不会要求旧 SSH 私钥。数据库角色由部署初始化脚本创建。

4. 将 `.dump` 和校验文件上传到新服务器的私有目录，校验后执行恢复。将示例文件路径替换为实际路径：

```sh
sh ops/backup/restore.sh /absolute/path/to/vault-backup.dump --confirm-replace
```

恢复命令始终要求显式确认参数，包括空的新数据库。它先在隔离临时数据库检查格式与兼容性；如已有密码库，则先保存回退备份，再停止应用并替换数据。失败时不要手动初始化一个新密码库覆盖旧数据，应检查错误和已保存的回退材料。

5. 在 Windows 客户端源码根目录重新设置 SSH 连接资料：

```powershell
.\console.ps1 -Action Configure
.\console.ps1 -Action Check
.\console.ps1 -Action Open
```

配置入口询问新地址、SSH 用户和本机新私钥路径，保存在 `.local/`。首次连接核对新主机指纹；不要为了绕过主机指纹变化而关闭校验。私钥只在本机 SSH 连接阶段使用，不上传给应用。

6. 在管理页输入原主密码或恢复密钥，验证账号、回收站、设置和日志。首次登录建立新服务器的查询启动信封，此后服务重启可自动恢复查询，管理端仍需登录。
7. 检查微信和模型授权。备份中的设置保持加密，但外部服务可能使旧令牌失效，此时重新扫码或配置；它们与 ECS 密钥无关。

## 1.0 旧备份与原机升级

旧 `.tar.gz` 必须包含原配套 `database.dump` 与 `vault.json`。只有旧 `database.dump` 无法恢复密钥信封；新格式则没有这个外部依赖。

旧包恢复使用相同命令，将文件名替换为旧归档；工具在临时库中提示隐藏输入原主密码或恢复密钥，验证加密数据、导入原始信封字节，之后才替换目标数据库。

对仍运行 1.0 的原服务器，先在新源码的 `.env` 中将 `VAULT_STATE_DIR` 指向旧状态根目录（其下应有 `data/`、`secrets/` 等目录），不要误用空的新目录。构建新应用镜像后，执行 `sh ops/backup/backup.sh --legacy`，保存输出的旧格式回退包。再执行 `sh ops/backup/restore.sh <该旧包的绝对路径> --confirm-replace`，在临时库中输入原凭据，完成验证和显式迁移。迁移不重新加密记录、不生成替代数据密钥；重复导入相同信封会验证已导入的数据。不要单独调用初始化接口来绕过“缺少密钥信封”的错误。

回退 1.0 必须同时恢复旧程序、旧数据库和旧信封。Git 标签只回退代码，不能回退数据库或机器密钥。所有迁移、备份与恢复共用维护锁，收到占用提示时等待已有操作结束。

## 隔离验收工具

`ops/checks/recovery.py` 专用于合成数据：它在显式给出的本地 PostgreSQL 测试服务创建随机命名的独立数据库，通过真实 HTTP 生成和下载备份，然后恢复到另一个新库、新目录和新机器密钥；最后清理它创建的测试数据库。

必须在带 PostgreSQL 17 客户端的应用镜像中运行，设置 `VAULT_TEST_ADMIN_DSN` 并显式传入 `--confirm-isolated`。不要使用正式数据库作为测试服务，也不要将整个包含 `.local` 的工作区挂载进测试容器。仅挂载检查脚本目录即可。

默认生成超过 512 MiB 的不可压缩合成加密数据，测量应用内存高水位，在下载中途注销，确认新请求被拒绝而当前传输可完成，并验证恢复后的密文、序列、设置、日志和主密码/恢复密钥登录。`--quick` 跳过大文件场景，只用于调试，不能代替完整发布验收。工具输出测试报告，不代表正式库已经恢复验证。
